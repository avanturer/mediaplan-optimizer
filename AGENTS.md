# Инструкции для ИИ-агентов проекта MediaPlan Optimizer

Этот файл действует на весь репозиторий. Он нужен, чтобы команды планировщика,
симулятора и сервиса исполнения разрабатывали совместимые компоненты и не
использовали скрытую информацию модели мира.

## Что прочитать перед изменениями

1. `Project description.md` — продуктовая постановка и границы хакатона.
2. `docs/WORLD_MODEL.md` — технический контракт модели мира и симулятора.
3. Тесты и README конкретного модуля, если они уже появились.

Если документы расходятся, не выбирайте трактовку молча. Продуктовые требования
из `Project description.md` имеют приоритет, а технический контракт нужно
синхронизировать отдельным изменением.

## Цель системы

Собрать локальный proof of concept замкнутого контура:

`бриф -> медиаплан -> почасовая симуляция -> наблюдение -> перераспределение`

Восемь абстрактных рекламных каналов работают в синтетическом изменчивом мире.
Оптимизатор должен удерживать кампанию ближе к утверждённой траектории, чем
статическое распределение бюджета, особенно после рыночного шока.

## Архитектурная граница

Разделяйте четыре роли:

- **World model** хранит истинные параметры, скрытое состояние и сценарий.
- **Simulator engine** применяет action и переводит мир на один час вперёд.
- **Observation boundary** формирует только доступные кампании агрегаты.
- **Optimizer / execution service** сравнивает факт с планом и формирует новый
  action.

Оптимизатор не импортирует внутренние классы мира и не читает конфигурацию со
скрытыми параметрами. Интеграция идёт через публичный каталог и `reset/step`.

## Неподвижные требования к модели мира

- Один вызов `step` соответствует одному часу кампании.
- Кампания длится 14–21 день и проигрывается за секунды.
- Обработка пакетная: не создавайте объект на каждый показ или пользователя.
- Каналы абстрактные; нельзя выдавать параметры за статистику VK, Ozon и других
  реальных площадок.
- В MVP используются три семейства поведения: auction, marketplace, direct/SMS.
- Мир нестационарен: суточный профиль, насыщение, fatigue и сценарные шоки.
- При нулевом лимите канал не расходует бюджет.
- Всегда выполняются `spend <= cap`, `unique_reach <= impressions` и
  `conversions <= clicks`.
- Одинаковые seeds, версия каталога и scenario дают воспроизводимую траекторию.
- Сравнение стратегий выполняется на одной ленте экзогенных случайных событий.

## Контракт с оптимизатором

Рекомендуемый доменный интерфейс:

```python
observation, info = simulator.reset(seed_bundle, scenario_id)
observation, metrics, terminated, info = simulator.step(action)
```

Минимальный `action`:

```json
{
  "spend_caps": {
    "social_1": 10000.0,
    "programmatic": 15000.0,
    "marketplace_1": 12000.0,
    "sms": 5000.0
  }
}
```

Обязательные почасовые поля наблюдения по каждому каналу:

`requests`, `impressions`, `unique_reach`, `clicks`, `conversions`, `spend`,
`ecpm`.

План, целевая траектория и reward не являются скрытой физикой мира. Их хранит
сервис исполнения. Gymnasium-адаптер может вычислять reward поверх доменного
контракта, не меняя симулятор.

## Защита от leakage

В публичные ответы нельзя включать:

- истинные будущие CPM/CTR/CR;
- расписание будущих шоков;
- скрытые остатки аудитории или инвентаря;
- параметры распределений и latent regime;
- oracle-прогноз следующих часов.

`info` в публичном режиме содержит только безопасные идентификаторы, ошибки
валидации и hashes конфигураций. Для тестов допустим отдельный privileged debug
snapshot, но его нельзя передавать стратегии.

## Требования к оптимизатору

- Работайте только с публичным каталогом, медиапланом и накопленными
  observations.
- Не предполагайте конкретный класс симулятора или формулу генерации метрик.
- Соблюдайте общий и канальные бюджеты, неотрицательность и допустимые шаги
  изменения лимитов.
- Поддерживайте минимум static baseline; желательно также proportional pacing,
  PID и greedy marginal-ROI baseline.
- Решение должно корректно работать при нулевых метриках, остановке канала и
  задержке/отсутствии отклика.
- Не оптимизируйтесь под один seed или один сценарий.

## Seeds и честное сравнение

Логически различайте:

- `catalog_seed` — генерация публичного каталога;
- `world_seed` — скрытые параметры и начальное состояние эпизода;
- `noise_seed` — почасовая экзогенная случайность;
- `scenario_id` — детерминированное описание шоков.

Простой `reset(seed)` может детерминированно выводить эти sub-seeds, но во
внутренних логах они должны быть различимы. Не расходуйте один последовательный
RNG внутри ветвящейся логики: используйте ключи вида
`(noise_seed, hour, channel_id, event_type)`, иначе разные actions разрушат
парность эксперимента.

## Проверки перед завершением изменений

Для модели мира или симулятора обязательны тесты:

- детерминизм `reset/step`;
- инварианты и граничные значения;
- отсутствие leakage в public schema;
- нулевой и очень большой cap;
- начало, окончание и recovery шока;
- одинаковая экзогенная лента для сравниваемых стратегий;
- полный прогон 21 день × 24 часа × 8 каналов;
- сериализация результата и повтор запуска из сохранённой конфигурации.

Для оптимизатора дополнительно сравните стратегию со static baseline минимум на
30 paired seeds и отчитайте среднее, разброс, нарушения ограничений и результат
после шока. MAPE используйте вместе с абсолютным отклонением или WAPE, поскольку
MAPE нестабилен около нуля.

## Что не добавлять без отдельного решения команды

- микро-аукцион для каждого показа;
- реальные API рекламных кабинетов;
- user-level данные и персональные идентификаторы;
- полноценную MMM или multi-touch attribution;
- GPU-зависимость;
- многоагентную конкуренцию;
- сложную RL-инфраструктуру, если задачу решает простая проверяемая стратегия.

## Работа с открытыми решениями

Источники и конкретные заимствуемые идеи перечислены в
`docs/WORLD_MODEL.md`. Не копируйте внешний код без проверки лицензии и
фиксации NOTICE/атрибуции. В MVP источники прежде всего задают архитектурные
паттерны и baseline-алгоритмы, а не требуют форка одного из проектов.
