# Кабинет: замечания рецензентов, не внесённые в код

Дата: 05.09.2026, вечер. Ветка `feature/pm-cabinet-ux`, файл `app/static/index.html` (после коммита `1b5cc07`), местами `app/main.py`, `README.md`, `docs/cabinet_changes.md`.

Два независимых разбора после переписывания кабинета: редактор (язык интерфейса) и инженер (логика, состояния, контракт с API). **В код ничего из этого не внесено** — PM не успевает до дороги. Документ для того, кто будет вносить.

## Как вносить

- Тексты интерфейса — по правилам `/ru-text` и `/humanizer-ru`: живой русский без калек, тире «—», «ёлочки», неразрывный пробел перед ₽ и % (в JS-строках ` `, в HTML `&nbsp;`; функции `rub()` и `pct()` уже ставят его сами). Обычные пробелы внутри JS-выражений (`% 100`, `% 24`) не трогать — это операторы.
- Технические элементы, которые не должен видеть рекламодатель, помечаются классом `tech`: в уровне «Кабинет» они скрыты правилом `body[data-level=simple] .tech{display:none}`.
- После правок: `set -o pipefail && .venv/bin/ruff check app tests && .venv/bin/python -m pytest -q tests/test_app.py`. Проверка в браузере: пример «1,2 млн ₽ на 21 день» → «Утвердить план» → «Запустить кампанию» → «К итогу», в обоих уровнях.
- Коммиты в ту же ветку, без соавторов-ботов в сообщениях.
- Строки в таблицах указаны по состоянию файла на момент разбора; после первых правок ищите по тексту «сейчас», не по номеру.

## Часть 1. Редактор: язык интерфейса

Найдено 45 мест. Из них три грамматические ошибки в коде, 24 места без неразрывного пробела, пять имён одной и той же стратегии.

### Решения PM по спорным пунктам

- Кнопку «Что если бюджет −10 % / +10 %» переименовать в «Что если бюджет ±10 %», а не в «Бюджет ±10 %»: без «что если» кнопка не объясняет, что делает.
- Плитка «Бюджет» в постановке B: «по медиане: цели хватит в половине случаев», не «средний» — бюджет медианный, слово «средний» соврёт.
- «Цена бездействия» в `docs/cabinet_changes.md` остаётся как имя поля для коллег; в интерфейсе уже «Если не делать».
- Всё остальное из таблиц ниже — принять.

Проверено и менять не надо: «2 271 конверсия», «на двое/трое/четверо суток», «+ 1 свой шок / 2 своих шока / 5 своих шоков», «обещание выполнено» — согласование верное; кавычки «ёлочки», тире «—», многоточие одним символом; точек в подписях плиток и подсказок нет единообразно, в абзацах `.muted` есть — тоже единообразно.

### Словарь терминов

«План без изменений» (кратко «без изменений») — единственное имя стратегии `static` в «Кабинете», «Стенде», README и docs; «заморозка», «план буквально», «без перераспределения» уходят. «Наше ведение» — имя стратегии `adaptive` в «Стенде» и документах; в «Кабинете» отдельного имени нет, это просто «факт». «Перенос» — любое перемещение денег между каналами в «Кабинете» (лимит, карточки, лента, итог); «ход» допустим только в docs как синоним. «Вариант» — три предложения планировщика в демо 2 (Кабинет и README). «Карточка» — предложение переноса, ждущее решения (оба уровня). «Слом канала» — в «Кабинете»; «детектор» — в «Стенде» и документах. «Рынок» и «случай» — в «Кабинете» вместо «мир»; «мир», «зерно», «сценарий» — в «Стенде» и документах. «Разброс ±N %» — в «Кабинете»; «коридор ±1σ» — в «Стенде». «Обещание» без «клиенту» — в «Кабинете»; «обещание клиенту» — в README и docs. «Событие» — общее слово для ленты (шок рынка, свой шок, слом); «шок» — в «Стенде». «Накопительно» — единая форма в плитках и графиках, «накопит.» только в узких заголовках таблиц.

## Часть 2. Инженер: логика и контракт

Проверено: оба файла целиком, синтаксис JS, curl ко всем восьми эндпоинтам (демо 1, демо 2, «с запасом» в B, decide approve/decline, compare/stress/degradation с замером времени, граничные случаи), живая страница при 1280 и 1000 px (computed style, ширина документа, переключение уровня посреди прогона, решение по карточке).

### В каком порядке чинить (решение PM)

1. Инженер 1 — план приходит уже утверждённым. Три строки, и **перед показом перезапустить uvicorn**: без перезапуска первый же клик «демо 1» на сервере, где план утверждали на репетиции, покажет два «текущих» этапа.
2. Инженер 3 — сброс этапа «Итог» в `prepareRun`. Одна строка.
3. Инженер 2 — «с запасом» в постановке B: цель клиента в полосе этапов и вердикте, защита от недостижимого второго плана.
4. Инженер 4, 16, 14, 18 — карточка, ждущая решения, в конце; лишние 22 px у кнопок без подписей; техника, видимая в «Кабинете»; неразрывные пробелы.
5. Редактор: три ошибки падежей и словарь терминов (перенос, план без изменений, слом канала, рынок).
6. Всё остальное по мере сил.

### Сломано на демо

1. **`renderPlan` / `showRunSection` + `main.py` (`/api/plan`, `/api/plan/{id}/approve`) — план приходит уже «утверждённым», а полоса этапов говорит обратное.** `plan_id` детерминирован по брифу, сервер помнит утверждение, поэтому повторный `POST /api/plan` того же брифа возвращает `approved_version: 1` (проверено: свежий бриф → approve → тот же бриф → `approved_version=1`). `renderPlan` ставит этап 2 «прогноз … · не утверждён» `cur`, потом `showRunSection` ставит этап 3 `cur`: два текущих этапа, бейдж «утверждён, версия 1», кнопка «Утвердить план» на месте, раздел 3 открыт без шага утверждения. Воспроизведение: демо 1 → Утвердить → демо 1 ещё раз. Правка: в `renderPlan` `stage('plan', p.approved_version ? `утверждён · …` : `прогноз … · не утверждён`, p.approved_version ? 'done' : 'cur')` и прятать или отключать `#btn-approve` при `approved_version`.

2. **`makePlan` (двойной расчёт), `stage('brief')`, вердикт демо 2 — «с запасом» в постановке B подменяет цель клиента.** Второй план считается под цель/(1−corridor), и его `brief.target_value` попадает в этап 1: «75 825 кликов · 14 дней» при введённых 50 000 (проверено в браузере). Хуже: если второй план недостижим, вердикт пишет «меньше цели 54 023» с вариантами под цель, которую никто не задавал, а вариант «снизить цель до 35 451» снова раздувается → снова недостижимо (узкий пресет: 35 451 достижимо, 54 023 нет — зацикливание, план «с запасом» на узком наборе получить нельзя). Правка: если второй план `infeasibility` — показывать базовый план с пометкой «резерв недостижим, план медианный»; в `stage('brief')` и вердикте брать `PLAN._promise.value` (исходную цель), а не `b.target_value`.

3. **`prepareRun` — после решения по карточке этап 4 остаётся «текущим» со старыми цифрами.** `prepareRun` прячет `#summary`, но `stage('summary')` не сбрасывает: остаётся `cur` «обещание выполнено · 2 181 конверсия» из прошлого прогона, клик по этапу ничего не делает (проверено: К итогу → час 12 → Перенести). То же при повторном «Запустить кампанию». Правка: в `prepareRun` добавить `stage('summary', 'в конце кампании', 'off')`.

### Ошибки логики

4. **`showHour`, карточки — в конце кампании карточка, ждущая решения, не видна.** Показываются последние 4 из 9 переносов; ждущий час 12 за бортом. Сводка пишет «Не решено вовремя: 1 карточка», действовать негде. Правка: всегда добавлять ждущие карточки первыми: `[...pending, ...cards.slice(-4)]` с дедупликацией.

5. **`whatIf` / `stressTest` не проверяют `PLAN !== plan` после `await`** и пишут в `#whatif` / `#stress` того плана, что отрисован сейчас → результат старого плана под новым. Воспроизведение: «Что если» → сразу демо 2. Правка: `const plan = PLAN; … if (PLAN !== plan) return;`.

6. **`compareStrategies` / `degradationTest` вставляют `box` в `#run-body`, а `runCampaign` / `decideProposal` заменяют `#run-body.innerHTML`** → box отрывается, результат минуты счёта теряется молча, кнопка разблокируется. Правка: отключать `#btn-run` на время стендов или проверять `box.isConnected` и выводить сообщение.

7. **Кнопки-примеры не блокируются во время `makePlan`.** Двойной клик демо 1 / демо 2 → два параллельных расчёта, побеждает последний ответ, он может не совпадать с формой (форма в B, план A). Правка: общий флаг `busy` или отключать оба `#btn-demo*` вместе с `#btn-plan`.

8. **`makePlan` — коридор берётся у первого плана**, у второго он другой (0,3406 → 0,3377), поэтому `p10 ≥ цель` не гарантирован, а плитка утверждает «цель внутри разброса даже по нижней границе». Правка: после второго плана проверять `plan.forecast.p10 >= target` и формулировать плитку условно.

9. **`renderSummary` — «с запасом» в B: «обещание выполнено» меряется от 50 000, а «Отклонение по кликам» и «Порог кейса» — от `promised_kpi` = 75 838.** Рекламодатель видит «выполнено» рядом с большим отклонением. Правка: подпись плиток «от плана с резервом» либо считать отклонение от обещания.

10. **`renderScenarioOpts` / `updateRunCaption` — при сроке меньше 11 дней все сценарии `na` (события с 240 ч), но `FORM.scenario` остаётся `channel_pause`, и в «Кабинете» (где карточки скрыты) подпись «на рынке: programmatic выключен на трое суток» врёт.** Правка: в `updateRunCaption` добавлять «— за горизонтом, не случится» или автоматически переключать на `stable`.

11. **`degradationTest` с параметром `pause` гоняет множители 0,8…0,2, что для паузы бессмысленно;** в таблице `×${x.multiplier}` печатается с точкой («×1.5»). Правка: для `pause` не запускать (или множители `[1]`), `String(x.multiplier).replace('.', ',')`.

12. **`addShock` пропускает дубли (тот же канал/параметр/день) и шоки по каналам с нулевым бюджетом** (`allocations` содержит все 8 каналов даже при `is_empty`, `_check_shock_target` тоже смотрит на allocations). Мелочь.

13. **`histogram` при пустом `per_run` молча выходит,** остаётся пустой canvas без подписи. Правка: писать «нет данных» в контейнер.

### Проверено и в порядке

Синтаксис JS; все имена полей, которые читает фронт, есть в ответах API (`/api/plan` — `forecast.p10/p50/p90`, `corridor_rel`, `is_empty`, `infeasibility.suggestions[].changed_field/suggested_value/applicable/why_not/binding_title`, `allocations[].marginal_cost_per_1000_kpi_rub`; `/api/run` — `main.hours[].by_channel/caps/reserve/events/status`, `proposals[].cpa_delta_pct/inaction_kpi_shortfall_pct/applied_by`, `frozen.hours`, `verdict.*`, `custom_shocks`, `seeds`, `decisions`; `decide` — `effect.kpi_delta/spend_delta/deviation_kpi_before/after`; `compare` — `mean/ci95/win_rate_vs_static/mean_actual_kpi/mean_actual_spend/per_run/within_threshold_count/title`; `stress` / `degradation` rows; `meta.catalog.channels[].sms.send_hours`).
